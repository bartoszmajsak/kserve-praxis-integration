Praxis data plane · repositories read 2026-11-19

Context

Moving the data plane from Gateway API on Istio to Praxis changes how a KServe LLMInferenceService receives traffic. The move exposes problems in the integration between MaaS and KServe. A status contract on the LLMInferenceService, with MaaS as the owner of the routing, can help in the overall migration process.

Problem MaaS and KServe integrate through the HTTPRoute

MaaS looks up the route, attaches its policies to it and derives the tenant from it. Praxis removes the per-model route.

What can help A status contract, and MaaS writes the routing

KServe publishes the backend, the port, the model names and Ready in the service status, with or without a route. MaaS writes the routing into the tenant's Proxy from it. The details are in Decision.

Migration In stages, per tenant

MaaS and KServe can prepare now. The cut-over moves a tenant at a time and waits on proxy deployment, the EPP client and the policy engine in Praxis.

Praxis in the request path

gateway-controller is not an ingress controller (yet?). It configures a Praxis proxy that is deployed behind the platform's existing ingress. Currently, that ingress ("any GWAPI provider, or none") "just forwards to it". A Gateway can still be the entry point and forward all traffic to Praxis. The per-model HTTPRoute is removed. Praxis routes on the model field of the request body, and "no route is ever written".

Shortcomings in today's integration

Currently, MaaS and KServe integrate through the HTTPRoute and not through a defined contract. MaaS looks up the route, attaches its policies to it and derives the tenant from it. KServe publishes the status MaaS needs only while a route exists. Praxis removes the route, so the items below have to be fixed before a service can be served through Praxis.

Gateway API support in Praxis

We checked whether Praxis has a Gateway API implementation that could serve the HTTPRoute KServe already generates. It does not have one we can rely on. The only Gateway API code is in the Rust operator, and new work happens in gateway-controller: rendering the Praxis config and deploying the proxy are tracked there (#14 to #17). The design also rules out a separate Gateway API controller next to it, because the Gateway API implementation "must therefore be the same controller that implements the Praxis Core API" (api.md, section 12). gateway-controller has no Gateway API code, and none of its 49 open issues is about it.

The operator also cannot serve the HTTPRoute that KServe generates. It passes Gateway API HTTP conformance, core and extended, but thirteen of the sixteen rules in KServe's route preset point at an InferencePool, and the operator accepts core/Service only (src/gateway_api/route_status.rs:142-148 at 1a9f9d5).

  • The operator has no tags, no releases and no users in the demos. A maintainer wrote on 2026-11-13 that they are "considering archiving" it once gateway-controller covers conformance.
  • No HTTPRoute support is being built for Praxis today. The AI Gateway API has no Gateway API dependency by design. Gateway API support is only mentioned as something for later ("When we implement GWAPI for praxis", policy#104, 2026-11-17), with no issue and no date.
  • The HTTPRoute does not need translating. Most of it is specific to Gateway API. Six pieces of information have to be passed on, and only KServe has them: the backend (pool or Service, name, port), which request paths go through the EPP and which go to the Service directly, served model names including LoRA adapters, backend TLS and its trust anchor, lifecycle (ready, stopped, deleting), and group and weight if the service stays the canary API.
  • Not available unless Praxis implements them: the catch-all rules that send non-inference paths such as /v1/models to the Service, and the unlimited request timeout.

Not verified

The findings are based on reading code, issues and the proposal. The following was not verified.

  • Nothing was run on a cluster. What the operator does with KServe's route is read from code.
  • Whether PR #26 on gateway-controller is still the intent. It was last pushed on 2026-11-12 and is unapproved. The pivot to the current proposal is not in any public thread.
  • How the proxy is deployed. gateway-controller has open issues for the Proxy ConfigMap, Deployment and Service (#15 to #17) and nothing merged.
  • That the Praxis ext_proc client cannot do TLS. This is inferred from its config and dependencies.
