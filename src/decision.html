Decision record · Praxis data plane

MaaSModelRef only, ModelProvider later

Moving the data plane from Gateway API on Istio to Praxis removes the per-model HTTPRoute, which is the object MaaS and KServe integrate through today. The preferred way to replace it keeps MaaSModelRef as the object users write. KServe publishes the backend in the LLMInferenceService status, and MaaS writes the routing into the Proxy of the tenant. The ModelProvider API can be adopted later.

Status Preferred option

It was discussed as option 3. Options 1 and 2 are described in Alternatives.

Decision MaaS writes the routing into the tenant's Proxy

KServe publishes the backend, the port, the model names and Ready in the service status, and MaaS reads it for each MaaSModelRef. No ModelProvider is created.

Next step ModelProvider when its API is defined

MaaS then creates one provider per MaaSModelRef. Users and KServe change nothing.

Context

Praxis routes on the model name in the request body, and no per-model HTTPRoute is written. Today MaaS looks up that route, attaches its policies to it and derives the tenant from it, and KServe publishes the status MaaS needs while the route exists. In the Praxis design the object that replaces the route is the ModelProvider, and its API is still open (#40, #42). The request path, the problems the move exposes and the state of Praxis are described in Context.

Goals and non-goals

We took the goals from what users, clients and the two controllers must not lose in the move. The non-goals are left out on purpose, to keep the first step small.

Goals

  • Models published through MaaS are served through Praxis without a per-model HTTPRoute.
  • Users and the dashboard keep writing the same objects. Clients keep the hostname, the request URL with the model in the body, and the model ID.
  • MaaS and KServe integrate through one contract, the LLMInferenceService status, and every object has one writer.
  • Upstream KServe needs no Praxis types and no tenant concept.
  • The first step does not wait for APIs that are still open in Praxis, and the ModelProvider can be adopted later without a user-facing change.
  • A tenant can move in stages and be rolled back, and the preparation can start before Praxis is ready.

Non-goals

  • Praxis routing for services that are not published through MaaS. They stay on Gateway API with Kuadrant.
  • Gateway API support in Praxis, or a translation of the HTTPRoute that KServe generates.
  • Replacing MaaSModelRef as the object users write, or defining the ModelProvider API.
  • Canary and weighted routing between services in the first step. The owner of the weights is still open.
  • An ingress without Gateway API. The tenant Gateway stays in front of the proxy.
  • Per-model path URLs of the form /<namespace>/<name>/v1/... through Praxis.
  • Moving a single model. The unit of the cut-over is the tenant.
  • Closing the gaps in Praxis itself: proxy deployment, the EPP client and the policy engine. We depend on them and track them.

Decision

We keep MaaSModelRef as the only object a user writes to publish a model. KServe publishes what it already knows about the service in its status: the backend, the port, the served model names and Ready, with or without a route. MaaS reads that status and writes the routing of each published model into the Proxy of the tenant, next to the policy slot, and gateway-controller renders it. No ModelProvider is created.

The status also has to say which request paths go through the EPP and which go to the workload Service directly. That split is only defined in the HTTPRoute today, and the routing MaaS writes needs both kinds of entries.

Benefits

  • One contract between MaaS and KServe: the LLMInferenceService status. MaaS no longer depends on the HTTPRoute, its labels, its parent Gateway or its hostnames.
  • One writer per object. MaaS writes every object in the tenant namespace, and KServe writes only next to the service.
  • Dependencies in one direction. KServe needs no tenant information, creates no Praxis object and does not depend on a Praxis CRD being installed, so upstream KServe stays vendor-neutral.
  • No dependency on the ModelProvider API. It is open with no milestone, and this option needs the Proxy and the Policy only.
  • Nothing changes in what users and the dashboard write. MaaSModelRef needs no new spec field.
  • Several tenants per service need no extra API. One service can be published to several tenants today, with one MaaSModelRef each.
  • The ModelProvider can be adopted later without a change for users or for KServe, because the contract with KServe and the user-facing objects stay the same.
  • It follows existing practice. MaaS already reads status.router.scheduler.inferencePool and writes an InferenceObjective per pool.

Costs and limits

  • In the current draft a routing change rolls the proxy pods. A Proxy has no field for a mounted routing file, so the routing is part of the rendered configuration. The draft that renders the proxy (gateway-controller#82) sets a revision of that configuration as an annotation on the pod template, so the Deployment rolls on every change.
  • Today it covers services without a scheduler, and no canary. The Praxis EPP client takes one static target and has no TLS. The alternatives have the same limit until that client is extended.
  • All models of a tenant are in one object, so every publish and unpublish is a write to the same Proxy.
  • The routing renderer in MaaS is discarded when the ModelProvider arrives. MaaS then creates one provider per MaaSModelRef.
  • A service without a MaaSModelRef has no routing entry, so non-MaaS services remain on Gateway API with Kuadrant.
  • Stopping or deleting a service removes its pool and its Service immediately. MaaS has to remove the routing entry at the same time.
  • Canary weights need an owner. They are either read from group and weight on the service, or defined in MaaS. We would not add a weight field to MaaSModelRef, because it would compete with the weight of a ModelProvider later.

Adopting the ModelProvider later

The preferred option is the first step towards option 2 in Alternatives, where MaaS creates one ModelProvider per MaaSModelRef. The step can be taken when the API is defined and implemented.

  • gateway-controller adds the type, its controller and the routing that is generated from it.
  • MaaS stops writing routing entries into the Proxy, creates one ModelProvider per MaaSModelRef, and hands the routing slot of the tenant to gateway-controller.
  • KServe changes nothing, because the status contract is the same.
  • Users change nothing, because MaaSModelRef stays the object they write. The Praxis design maps it the same way: a MaaSModelRef becomes a Model and a ModelProvider (docs/design/api.md:549).
  • Which ModelProvider arrives is open. The design in the repository and the proposal describe different fields, and the design leaves weighting and failover out of scope (docs/design/api-v1alpha1.md:386-387).

Impact on users and the dashboard

The goal is that users and the dashboard notice nothing. While the route and the routing in Praxis exist in parallel, nothing changes for them. The end state needs care, because the dashboard and MaaS both rely on fields that a service without a route would no longer have. Keeping those fields, and letting KServe skip the route for a Gateway that opts in, avoids that.

What cannot be hidden

  • Per-model path URLs of the form /<namespace>/<name>/v1/... stop working unless Praxis serves paths. Setting serving.kserve.io/model-based-routing-only on a Gateway has the same effect for clients today, so it can be used to find affected clients first.
  • The Kuadrant objects disappear, together with the documented kubectl get authpolicy and tokenratelimitpolicy checks and the status fields that list those objects.
  • The HTTPRoute column of MaaSModelRef is empty, and two steps disappear from the progress list in the dashboard.
  • AFAICT rate limit counters restart at the cut-over.

Migration

A tenant can move in stages, with the tenant Gateway kept as the ingress. The preparation in MaaS and KServe can start now, and the cut-over waits on work in Praxis. The stages, what each of them depends on and how each is rolled back are described in Migration, which is a work in progress.

Not verified

The decision is based on reading code, issues and the proposal. The following was not verified.

  • Nothing was run on a cluster. How services with no route behave is read from code. Two KServe unit tests covering the readiness path were run and pass.
  • That routing can stay MaaS-defined is taken from a remark in the proposal. What an inline filter chain in a Proxy can express was read from the types, and nothing renders it yet.
  • The pod roll on a routing change is read from the draft gateway-controller#82 at aa8180f. It was not run, and the draft can change before it merges.
  • The dashboard was read on main at 16366ea. Its release branches were not read, and nothing was exercised in a browser.
  • The MaaS change list comes from a single read of the code. We rechecked the rows about the route, the rate limit policy, maas-api, the InferenceObjective and the tenant Gateway, and took the rest from the note.
