Praxis data plane · MaaS

External models

External models are served through objects that exist only on Gateway API and Istio today, and the Gateway's Envoy opens the connection to the provider. With Praxis as the data plane the proxy can open that connection itself, and the same question arises as for KServe models: which component writes the routing. This is a MaaS concern and is not part of the Decision.

Today Envoy connects to the provider

ai-gateway-controller chooses the provider in a Praxis ext_proc filter and returns the choice to Envoy through an HTTPRoute. Istio objects configure the TLS.

With Praxis The proxy can connect to the provider

Praxis can connect to a provider over TLS, inject its credential and translate some API formats today. Weights work in one filter only, and failover is missing.

Open Which component writes the routing

The decision covers KServe models. For external models the documents we read name three different writers. We recommend MaaS.

Request path

The component that chooses the provider is the same in both setups, a Praxis filter. What changes is which component connects to the provider. Today that is Envoy, with Istio objects for the TLS. With Praxis as the proxy it is an upstream cluster of the proxy.

External models today

An external model is a model at a provider outside the cluster, such as OpenAI or Anthropic. We read how it is modelled and routed in ai-gateway-controller (AGC) at 02aa443 and in MaaS at e0afdbc.

Objects

  • ExternalProvider and ExternalModel are in the group inference.opendatahub.io/v1alpha1. Their Go types are in AGC (groupversion_info.go:28).
  • An ExternalProvider holds the provider type, its host name and a reference to the credential Secret (externalprovider_types.go:48-70). An ExternalModel holds the model name clients use and one or more provider references, each with a target model, an API format and a weight (externalmodel_types.go:48-127).
  • A user publishes an external model with a MaaSModelRef whose modelRef.kind is ExternalModel (maasmodelref_types.go:77-90).
  • MaaS does not create the route of an external model. It takes the route name from the status of the ExternalModel and checks that the route exists and is accepted by the Gateway (providers_external.go:63-66).
  • AGC writes the rest. It reconciles both kinds "into the tenant-local ExtProc overlay, credential projections, and Envoy-owned provider transport".

What AGC plans

AGC describes two modes for Praxis (praxis-dataplane-evolution.md:15-22). In gateway mode, which is the setup above, Praxis is an ext_proc side-call and Envoy opens the upstream connection. In standard mode Praxis is the tenant-facing gateway, the AI filters run in-process, and Praxis opens the connection.

  • Standard mode is a draft. The document calls it "Direction of travel from the research spike, not a committed product design", and says that authentication, quota and token accounting remain open.
  • In that draft Praxis "opens the connection to the generated KServe Service (or ExternalModel provider) without Envoy or Istio on the inference path".
  • AGC is named as the component that would "Compile Gateway / KServe / ExternalModel intent into Praxis runtime config".
  • We found no code for standard mode in AGC or in MaaS.

What the Praxis design says

The control-plane design in gateway-controller covers external providers with the same two objects it uses for models in the cluster. Neither is implemented (#40, #42).

  • A ModelProvider can name an external upstream URL in place of a Service, with a credential Secret and the header to present it in (api-v1alpha1.md:281-294).
  • The design maps ExternalProvider and ExternalModel to ModelProvider and Model as "Near 1:1", and calls it a candidate for MaaS to delegate. It lists the question as open (api.md:621).
  • Weighting and failover between providers are out of scope of the first API version (api-v1alpha1.md:386-387).

Recommended control plane

We recommend that the component that writes the rest of the Proxy of a tenant also writes the routing and the upstream clusters of its external models. Under the decision that is MaaS. AGC keeps resolving the providers and publishes the result in the status of the ExternalModel, which MaaS reads. This is a recommendation and has not been agreed.

Why this arrangement

  • One writer per Proxy. The filters of a chain are ordered, so two controllers that compose one chain depend on the output of each other.
  • The same contract as for KServe models. The component that knows the backend publishes it in status, and MaaS writes the Proxy.
  • The provider logic stays in AGC. Weights, references to providers in other namespaces, credential copies and the API format per provider are implemented there.

What it does not solve

  • Weights need the overlay file in the proxy, because inline candidates of intelligent_route cannot carry weights (intelligent_route.md:201-204). A Proxy has no field for a mounted file.
  • A Proxy offers Secret keys as environment variables only. AFAICT an environment variable does not follow a Secret rotation without a restart.
  • The alternative that is also consistent is AGC as the single writer of the Proxy, for KServe models and external models, as the AGC draft proposes. It reverses the decision that MaaS writes the routing of KServe models.
  • Later both kinds can move to ModelProvider and Model, rendered by gateway-controller.

Open points

The decision for KServe models has MaaS write the routing into the Proxy of the tenant. Nothing we read settles the same for external models. The points below are our reading of what is undefined.

  • Which component writes the routing of external models. The AGC draft names AGC, the Praxis design suggests that MaaS delegates to ModelProvider and Model, and the decision covers KServe models only. If MaaS writes the routing of KServe models and AGC that of external models, the Proxy of a tenant has two writers. We recommend MaaS, as described above.
  • What MaaS reads for an external model without the HTTPRoute. The status of the MaaSModelRef and the targets of the policies come from that route today.
  • How the credential reaches the proxy. Today the kubelet projects the Secret as a file into the ext_proc pod. The Proxy type offers Secret keys as environment variables only (proxy_types.go:41-43).
  • How a private CA is trusted. An ExternalProvider defines it in Istio terms, as a Secret in the Gateway namespace or a file mounted in the Gateway (externalprovider_types.go:65-69). Praxis needs the CA as a file in its own pod.
  • Weights and failover. Weights between providers work today. The Praxis design leaves them out of the first API version, and failover exists in neither.
  • How a new provider is added. It needs a new upstream cluster, so it is a change of the proxy configuration and not only of the routing data.
  • Token limits. They are as open for external models as for KServe models, and AGC lists them as open for standard mode (praxis-dataplane-evolution.md:203-204).
  • Egress through an HTTP proxy. Praxis has no upstream proxy setting, which matters for clusters that reach providers only through a proxy.

Not verified

The findings are based on reading code and design documents. The following was not verified.

  • Nothing was run on a cluster.
  • The two Praxis repositories were read at a59c927 and 2212314. Both have moved since, so a capability listed as missing may have been added.
  • That users write the ExternalProvider and the ExternalModel is inferred. We found no controller that creates them, apart from a migration of the older kind.
  • How Kuadrant reads the token usage from the response of a provider.
  • That no upstream proxy setting exists in Praxis is the result of a search, not a statement of the project.

## Request path

The component that chooses the provider is the same in both setups, a Praxis filter. What changes is which component connects to the provider. Today that is Envoy, with Istio objects for the TLS. With Praxis as the proxy it is an upstream cluster of the proxy.

![Request path of an external model today and with Praxis as the proxy](https://raw.githubusercontent.com/bartoszmajsak/kserve-praxis-integration/main/docs/figs/png/external-request-path.png)

Today a Praxis `ext_proc` server chooses the provider, and Envoy connects to it. With Praxis as the proxy the same filters run in-process, and the proxy connects to the provider. The right column follows the AGC draft and what Praxis offers today. It is not built.

### Today: who does what, and why

- The user writes the `ExternalProvider`, the `ExternalModel` and the credential Secret, and publishes the model with a `MaaSModelRef`.
- MaaS writes the `AuthPolicy` and the `TokenRateLimitPolicy` on the route, and takes the status of the `MaaSModelRef` from the route.
- AGC writes the routing data, the credential projections, the HTTPRoute and the Istio objects.
- Kuadrant enforces authentication and token limits in the Gateway.
- Praxis runs as two `ext_proc` servers. One reads the model name, the other chooses the provider, translates and adds the credential.
- Envoy, configured by Istio, connects to the provider.

### With Praxis: who does what, and why

- The tenant Gateway forwards to the proxy of the tenant. It no longer carries the routing of a model.
- Praxis chooses the provider, adds the credential, translates and connects to the provider, all in one process. No `ext_proc` call is involved.
- Which component writes the routing data and the upstream clusters is open. The AGC draft names AGC.
- How the MaaS policies for external models are enforced in the proxy is open.
- AFAICT the HTTPRoute, the `ExternalName` Service, the `ServiceEntry`, the `DestinationRule` and the `EnvoyFilter` objects are no longer needed.

The control-plane design in `gateway-controller` covers external providers with the same two objects it uses for models in the cluster. Neither is implemented ([`#40`](https://github.com/praxis-proxy/gateway-controller/issues/40), [`#42`](https://github.com/praxis-proxy/gateway-controller/issues/42)).

- A `ModelProvider` can name an external upstream URL in place of a Service, with a credential Secret and the header to present it in ([`api-v1alpha1.md:281-294`](https://github.com/praxis-proxy/gateway-controller/blob/f6a12554d9294130010ed16abea775657914bb6f/docs/design/api-v1alpha1.md?plain=1#L281-L294)).
- The design maps `ExternalProvider` and `ExternalModel` to `ModelProvider` and `Model` as ["Near 1:1"](https://github.com/praxis-proxy/gateway-controller/blob/f6a12554d9294130010ed16abea775657914bb6f/docs/design/api.md?plain=1#L550), and calls it a candidate for MaaS to delegate. It lists the question as open ([`api.md:621`](https://github.com/praxis-proxy/gateway-controller/blob/f6a12554d9294130010ed16abea775657914bb6f/docs/design/api.md?plain=1#L621)).
- Weighting and failover between providers are out of scope of the first API version ([`api-v1alpha1.md:386-387`](https://github.com/praxis-proxy/gateway-controller/blob/f6a12554d9294130010ed16abea775657914bb6f/docs/design/api-v1alpha1.md?plain=1#L386-L387)).

## Recommended control plane

We recommend that the component that writes the rest of the `Proxy` of a tenant also writes the routing and the upstream clusters of its external models. Under the decision that is MaaS. AGC keeps resolving the providers and publishes the result in the status of the `ExternalModel`, which MaaS reads. This is a recommendation and has not been agreed.

![Custom resources of an external model with MaaS as the writer of the Proxy](https://raw.githubusercontent.com/bartoszmajsak/kserve-praxis-integration/main/docs/figs/png/external-control-plane.png)

MaaS is the only writer of the `Proxy`. AGC writes the status of the `ExternalModel` and the copy of the credential Secret, and the user writes the rest. The marks are explained in [Alternatives](https://bartoszmajsak.github.io/kserve-praxis-integration/alternatives.html).

### Who does what, and why

- The user writes the `ExternalProvider`, the `ExternalModel`, the credential Secret and the `MaaSModelRef`, as today.
- AGC resolves the providers of an `ExternalModel` into its status: the host, the port, the TLS settings, the credential reference and the weight. It computes this today in a resolver that has no access to the cluster ([`resolver.go:1-2`](https://github.com/opendatahub-io/ai-gateway-controller/blob/02aa4430a07c484a76f5dbcb338ebd726fa48863/pkg/resolver/resolver.go#L1-L2)). It also copies the credential Secret into the tenant namespace, as it does today ([`attachment.go:72`](https://github.com/opendatahub-io/ai-gateway-controller/blob/02aa4430a07c484a76f5dbcb338ebd726fa48863/pkg/controller/attachment.go#L72)).
- MaaS reads that status and writes the routing and one upstream cluster per provider into the `Proxy` of the tenant, next to the entries for KServe models.
- `gateway-controller` renders and deploys the proxy, and the proxy connects to the provider.

### Why this arrangement

- **One writer per `Proxy`.** The filters of a chain are ordered, so two controllers that compose one chain depend on the output of each other.
- **The same contract as for KServe models.** The component that knows the backend publishes it in status, and MaaS writes the `Proxy`.
- **The provider logic stays in AGC.** Weights, references to providers in other namespaces, credential copies and the API format per provider are implemented there.

### What it does not solve

- Weights need the overlay file in the proxy, because inline candidates of `intelligent_route` cannot carry weights ([`intelligent_route.md:201-204`](https://github.com/praxis-proxy/ai/blob/a59c9270258a68c68f45419ef02d3f5a0a195fdd/docs/filters/intelligent_route.md?plain=1#L201-L204)). A `Proxy` has no field for a mounted file.
- A `Proxy` offers Secret keys as environment variables only. AFAICT an environment variable does not follow a Secret rotation without a restart.
- The alternative that is also consistent is AGC as the single writer of the `Proxy`, for KServe models and external models, as the AGC draft proposes. It reverses the decision that MaaS writes the routing of KServe models.
- Later both kinds can move to `ModelProvider` and `Model`, rendered by `gateway-controller`.

## Open points

The decision for KServe models has MaaS write the routing into the `Proxy` of the tenant. Nothing we read settles the same for external models. The points below are our reading of what is undefined.

- **Which component writes the routing of external models.** The AGC draft names AGC, the Praxis design suggests that MaaS delegates to `ModelProvider` and `Model`, and the decision covers KServe models only. If MaaS writes the routing of KServe models and AGC that of external models, the `Proxy` of a tenant has two writers. We recommend MaaS, as described above.
- **What MaaS reads for an external model without the HTTPRoute.** The status of the `MaaSModelRef` and the targets of the policies come from that route today.
- **How the credential reaches the proxy.** Today the kubelet projects the Secret as a file into the `ext_proc` pod. The `Proxy` type offers Secret keys as environment variables only ([`proxy_types.go:41-43`](https://github.com/praxis-proxy/gateway-controller/blob/f6a12554d9294130010ed16abea775657914bb6f/api/proxy/v1alpha1/proxy_types.go#L41-L43)).
- **How a private CA is trusted.** An `ExternalProvider` defines it in Istio terms, as a Secret in the Gateway namespace or a file mounted in the Gateway ([`externalprovider_types.go:65-69`](https://github.com/opendatahub-io/ai-gateway-controller/blob/02aa4430a07c484a76f5dbcb338ebd726fa48863/api/inference/v1alpha1/externalprovider_types.go#L65-L69)). Praxis needs the CA as a file in its own pod.
- **Weights and failover.** Weights between providers work today. The Praxis design leaves them out of the first API version, and failover exists in neither.
- **How a new provider is added.** It needs a new upstream cluster, so it is a change of the proxy configuration and not only of the routing data.
- **Token limits.** They are as open for external models as for KServe models, and AGC lists them as open for standard mode ([`praxis-dataplane-evolution.md:203-204`](https://github.com/opendatahub-io/ai-gateway-controller/blob/02aa4430a07c484a76f5dbcb338ebd726fa48863/docs/praxis-dataplane-evolution.md?plain=1#L203-L204)).
- **Egress through an HTTP proxy.** Praxis has no upstream proxy setting, which matters for clusters that reach providers only through a proxy.

## Not verified

The findings are based on reading code and design documents. The following was not verified.

- Nothing was run on a cluster.
- The two Praxis repositories were read at [`a59c927`](https://github.com/praxis-proxy/ai/commit/a59c9270258a68c68f45419ef02d3f5a0a195fdd) and [`2212314`](https://github.com/praxis-proxy/praxis/commit/2212314b12a4536774f41ed4e1aec1619d403459). Both have moved since, so a capability listed as missing may have been added.
- That users write the `ExternalProvider` and the `ExternalModel` is inferred. We found no controller that creates them, apart from a migration of the older kind.
- How Kuadrant reads the token usage from the response of a provider.
- That no upstream proxy setting exists in Praxis is the result of a search, not a statement of the project.
