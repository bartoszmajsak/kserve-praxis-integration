KServe, MaaS and Praxis integration

How a KServe LLMInferenceService that is published through MaaS is served when the data plane moves from Gateway API on Istio to Praxis: the decision, the alternatives and the context.

Decision

The decision: MaaSModelRef stays the object users write, KServe publishes the backend in status, and MaaS writes the routing into the tenant's Proxy. What it gains, what it costs and what changes in KServe and MaaS.

Alternatives

The options that were considered and not preferred, with the custom resources of each: which one references which, which one owns which, and which controller writes each.

Context

How a request reaches the model today and with Praxis, what the move exposes in the integration between MaaS and KServe, and what Praxis supports of Gateway API.

Migration

Work in progress: the stages in which a tenant can move to Praxis, what each stage depends on, what can start now in MaaS and KServe, and how each stage is rolled back.

Doc edition

The decision in the format of an Open Data Hub architecture decision record, for pasting into a doc. It leaves out the code references, the state of Praxis and the migration.
